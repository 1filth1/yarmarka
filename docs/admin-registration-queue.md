# Yarmarka CRM — административная очередь регистрации сотрудников

> Статус: UI/UX и backend contract. Документ не меняет текущий интерфейс или production.

## 1. Назначение

Добавить в административную часть CRM экран «Заявки на регистрацию», где администратор вручную рассматривает самостоятельные заявки будущих сотрудников. Отсутствуют SMS- и email-подтверждения. Подача заявки не создаёт активную учётную запись и не даёт доступа к CRM.

## 2. Расположение и доступ

- Раздел доступен только пользователям с доверенным custom claim `admin == true`.
- Предлагаемое место: отдельный пункт в административной навигации рядом с разделом «Сотрудники» либо вкладка внутри существующего раздела сотрудников.
- Для обычного сотрудника этот раздел и данные очереди недоступны не только визуально, но и через Firestore Rules / callable backend.
- Счётчик ожидающих заявок показывает число записей со статусом `pending`; его данные получает только администратор.

## 3. Список заявок

Колонки:

- Дата подачи.
- ФИО.
- Телефон.
- Запрошенный отдел.
- Логин, который пользователь хочет использовать (если логин собирается в форме).
- Статус: ожидает / одобрена / отклонена.
- Действия: открыть карточку.

Фильтры: статус, отдел, поиск по ФИО/телефону/логину, сортировка по дате (сначала старые ожидающие).

По умолчанию показывать `pending`. Одобренные и отклонённые доступны через фильтр/вкладки. Не выводить пароли, хеши, activation code или внутренние технические токены.

## 4. Карточка и решение администратора

Карточка заявки содержит все поля, переданные пользователем, дату подачи и статус. Администратор может:

- выбрать/исправить утверждённый отдел;
- одобрить заявку;
- отклонить заявку с необязательной причиной;
- просмотреть журнал предыдущих действий по заявке.

**Одобрение:** запросить подтверждение действия, вызвать защищённую callable function `approveStaffApplication`. Backend повторно проверяет роль администратора, статус `pending`, уникальность логина, допустимость отдела и отсутствие конфликтующей активной заявки. Затем выдаёт одноразовую активацию. UI показывает код один раз и предлагает передать его сотруднику вручную. Не сохранять код в браузерном хранилище, не выводить его в логи и не показывать повторно; если код потерян, администратор отзывает и выпускает новый.

**Отклонение:** запросить подтверждение, вызвать `rejectStaffApplication`, сохранить автора, время и причину. Отклонение не должно создавать Firebase Auth account.

## 5. API/backend contract

- `submitStaffApplication` — публичная callable function с App Check, строгой валидацией, защитой от спама и дубликатов; создаёт только `pending`.
- `listStaffApplications` — только admin; фильтры/пагинация выполняются сервером.
- `getStaffApplication` — только admin.
- `approveStaffApplication` — только admin; назначение отдела и выпуск одноразового activation code.
- `rejectStaffApplication` — только admin; запись решения и причины.
- `activateStaffAccount` — проверка одноразового кода и установка пароля; атомарная/idempotent обработка.
- `revokeActivationCode` — только admin; отзыв потерянного/скомпрометированного кода и выпуск нового.

Каждая административная операция должна проверять custom claims на сервере, не доверять переданному клиентом `role`, `uid`, `status` или `approvedByUid`, и писать audit event.

## 6. Состояния и UX

- **Ожидает:** заявка получена, доступа нет.
- **Одобрена — ожидает активации:** администратор разрешил создание аккаунта; сотрудник ещё не активировал логин/пароль, доступа нет.
- **Активна:** сотрудник завершил активацию и получил Firebase Auth UID.
- **Отклонена:** доступ не предоставляется.
- **Истекла:** срок одноразовой активации завершился; администратор может повторно выдать активацию после проверки.

Показывать понятные пустые состояния, индикатор загрузки, ошибки backend и повторное подтверждение опасных действий. Не считать заявку обработанной до успешного ответа backend.

## 7. Аудит и приватность

Журналировать подачу, просмотр (если это нужно политике организации), одобрение, отклонение, смену отдела, выпуск/отзыв активации и активацию учётной записи. В аудите хранить actor UID, timestamp, application ID, action и ограниченные метаданные; не сохранять пароли, хеши, коды активации или токены. Доступ к персональным данным заявителей только у администраторов.

## 8. Критерии приёмки

- Сотрудник не видит пункт меню, не может прочитать очередь прямым запросом и не может одобрить заявку.
- Неавторизованный пользователь может только отправить валидную заявку и не может читать заявки.
- Публичная регистрация создаёт только `pending`.
- Администратор видит очередь, открывает карточку, утверждает отдел, одобряет/отклоняет.
- Одобрение не выдаёт доступ до активации одноразовым кодом и установки пароля.
- Повторное нажатие «Одобрить» не создаёт дубликаты аккаунта/активации.
- Код показывается один раз, имеет срок действия и ограничение попыток.
- Все изменения ролей/статусов происходят на backend и аудируются.
- UI показывает актуальные состояния, а не локально предполагает успешный результат.
