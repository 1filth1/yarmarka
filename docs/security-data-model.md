# Yarmarka CRM — модель данных и матрица доступа

> Статус: проект целевой модели, не готовая production-конфигурация. Схема уточняется по результатам аудита и согласования бизнес-правил. Не разворачивать напрямую в production.

## 1. Что подтверждено аудитом текущего приложения

Основные текущие сущности и связи:

- Сотрудник: `users[]`, поля как минимум `id`, `fullName`, `phone`, `pin`, `role`, `departmentId`.
- Клиент/заявитель: `clients[]`, поля как минимум `id`, `name`, `email`, `phone`, `password`, `contractId`, `contractNumber`, `companyId`, иногда `isStaff`.
- Договор: `contracts[]`, поля как минимум `id`, `number`, `name`, `clientId`, `startDate`, `endDate`.
- Компания: `companies[]`, поля как минимум `id`, `name`, `domain`.
- Заявка: `tickets[]`, поля как минимум `id`, `number`, `subject`, `description`, `clientId`, `contractId`, `contractNumber`, `category`, `priority`, `status`, `assigneeId`, даты, `recurrence`, `recurringParentId`, `comments[]`, `history[]`.
- Комментарий внутри заявки: `id`, `authorId`, `authorType`, `text`, `createdAt`.
- История внутри заявки: `action`, `at`, `by`, `details`.
- Справочники: отделы, категории и настройки.

Подтверждённые связи:

- Договор ссылается на заявителя через `contracts.clientId`.
- Заявитель ссылается на договор через `clients.contractId` (в текущем UI обычно один договор на клиентский аккаунт).
- Заявка ссылается на заявителя через `tickets.clientId` и может ссылаться на договор через `tickets.contractId`.
- Заявка назначается сотруднику через `tickets.assigneeId`.
- Сотрудник относится к отделу через `users.departmentId`.
- Клиент может быть связан с компанией через `clients.companyId`.
- Комментарии и история пока вложены в документ заявки.

В текущем приложении есть также служебный сценарий, когда сотрудник создаёт заявку «от себя» и для этого создаётся запись клиента с `isStaff: true`, без договора. Новая схема должна сохранить этот сценарий как отдельный тип заявителя или явно заменить его.

## 2. Предлагаемая структура Firestore

Идентификаторы документов для профилей — Firebase Auth UID. Для остальных сущностей можно использовать новые случайные ID Firestore; старые ID сохранять как `legacyId` на время миграции и сверки.

| Коллекция | Назначение | Основные поля (черновик) |
|---|---|---|
| `users/{uid}` | Профили сотрудников | `uid`, `fullName`, `phone`, `departmentId`, `active`, `createdAt`, `legacyId` |
| `clients/{uid}` | Профили клиентов | `uid`, `name`, `email`, `phone`, `companyId`, `createdAt`, `legacyId` |
| `companies/{companyId}` | Компании | `name`, `domain`, `createdAt`, `legacyId` |
| `contracts/{contractId}` | Договоры | `number`, `name`, `clientUid`, `companyId`, `startDate`, `endDate`, `createdAt`, `legacyId` |
| `tickets/{ticketId}` | Заявки | `number`, `subject`, `description`, `clientUid`, `contractId`, `categoryId`, `priority`, `status`, `assigneeUid`, `departmentId`, `createdAt`, `updatedAt`, `resolvedAt`, recurrence fields, `legacyId` |
| `tickets/{ticketId}/comments/{commentId}` | Переписка | `authorUid`, `authorRole`, `text`, `createdAt`, `legacyId` |
| `tickets/{ticketId}/events/{eventId}` | Аудит событий заявки | `actorUid`, `action`, `details`, `createdAt`, `legacyId` |
| `departments/{departmentId}` | Отделы | `name`, `description`, `color`, `active`, `legacyId` |
| `categories/{categoryId}` | Категории | `name`, `color`, `active`, `legacyId` |
| `settings/{settingId}` | Настройки | только необходимые настройки; секреты и полномочия не хранить в клиентски доступных настройках |

### Важные уточнения модели

- В профиле клиента не хранить пароль. Пароль обслуживается Firebase Authentication.
- В профиле сотрудника не хранить PIN как средство авторизации. Сотрудник входит через Firebase Authentication; если короткий PIN нужен как дополнительное удобство, его нельзя использовать вместо полноценной аутентификации.
- Роль не должна назначаться из формы регистрации. Первого администратора создаёт доверенная процедура bootstrap; дальнейшее назначение ролей — только администратором через серверную функцию.
- Связь `contracts.clientUid` устанавливается сервером после проверки регистрации по договору. Клиент не может сам прислать UID владельца и привязать договор.
- Поля `clientUid`, `assigneeUid`, `departmentId`, `status`, `role`, `createdAt` и системные номера нельзя безусловно принимать от клиента при записи.
- Комментарии и события лучше вынести в подколлекции: это облегчает постраничную загрузку и независимую проверку прав. События истории предпочтительно создавать сервером, чтобы нельзя было подделать автора или содержание аудита.
- Если комментарии остаются вложенным массивом, обновление одного сообщения будет переписывать весь документ заявки; подколлекция предпочтительнее.
- Номер заявки должен выдаваться сервером транзакционно/через счётчик, а не вычисляться по загруженному браузером массиву.

## 3. Предварительная матрица доступа

| Ресурс / действие | Клиент | Сотрудник | Администратор |
|---|---|---|---|
| Свой профиль | читать; ограниченно обновлять контактные поля | читать; ограниченно обновлять свой профиль | управлять через доверенные операции |
| Чужие профили клиентов | нет | только минимальные поля, необходимые для работы с разрешённой заявкой (предлагается) | да |
| Договоры | только свои, безопасные для показа поля | только необходимые для разрешённых заявок/задач (уточнить) | да |
| Заявки | читать свои; создавать свои; ограниченно дополнять комментариями | читать/обрабатывать назначенные заявки (предлагаемая базовая политика) | все |
| Комментарии | читать свои переписки; добавлять клиентские сообщения в свои незакрытые заявки | читать разрешённые переписки; добавлять сообщения от своего UID | все |
| История событий | читать клиентскую часть истории, если она нужна в портале | читать историю разрешённых заявок | все |
| Справочники категорий | читать только опубликованные | читать активные | управлять |
| Сотрудники и роли | нет | минимальная информация коллег, необходимая интерфейсу | управлять через сервер |
| Настройки CRM | нет | только явно разрешённые настройки | управлять |

### Подтверждённые решения владельца проекта

1. **Сотрудник видит только заявки, назначенные лично ему.** Доступ ко всем заявкам отдела не предоставляется автоматически.
2. **Администратор видит все заявки** и может выполнять административные операции в рамках своей роли.
3. **Самостоятельная регистрация сотрудников сохраняется, но доступ выдаётся только после подтверждения администратором.**

Эти решения должны обеспечиваться серверными правилами, а не только фильтрами интерфейса.

### Целевой процесс регистрации сотрудника (без SMS и email)

Подтверждённый владельцем вариант: **самостоятельная подача заявки без SMS- или email-подтверждения; решение принимает администратор вручную.**

1. Пользователь заполняет форму: ФИО, телефон, желаемый отдел и другие необходимые сведения. Форма отправляет именно заявку на регистрацию, а не создаёт активную учётную запись сотрудника.
2. Сервер сохраняет заявку со статусом `pending`. До одобрения пользователь не получает роль `staff` и не имеет доступа к заявкам, клиентам, договорам, сотрудникам и внутренним настройкам CRM.
3. Администратор проверяет личность/право доступа вручную вне автоматической SMS/email-проверки, просматривает заявку и подтверждает либо отклоняет её.
4. При подтверждении доверенная серверная операция создаёт/активирует учётную запись, назначает роль `staff` и утверждённый `departmentId`. Данные для первого входа выдаются сотруднику вручную безопасным способом; способ и формат учётных данных нужно определить до реализации.
5. При отклонении заявка остаётся без привилегий. Повторная подача и срок хранения отклонённых заявок требуют отдельного решения.

**Важно по авторизации:** отсутствие SMS/email-проверки не означает, что можно использовать PIN из четырёх цифр как единственную защиту. Текущий PIN хранится в общем документе и проверяется клиентским JavaScript — эту схему нельзя переносить в новую систему. До реализации нужно выбрать серверную схему входа без SMS/email (например, логин + стойкий пароль с проверкой на доверенном backend и выдачей Firebase custom token либо другой проверенный механизм). Пароли должны храниться только в виде стойких хешей; ограничение попыток входа и аудит действий обязательны.

Статус заявки и роль назначаются только доверенным серверным кодом. Клиентская запись в Firestore не должна позволять пользователю выставить себе `approved`, `active`, `staff` или `admin`.

### Обязательная политика видимости заявок

- Сотрудник: чтение и обработка только заявок, где `assigneeUid == request.auth.uid`.
- Администратор: чтение всех заявок.
- Клиент: чтение только заявок, где `clientUid == request.auth.uid`.
- Сотрудник не может получить доступ к чужой заявке изменением параметров запроса или подстановкой ID документа.
- Если заявка переназначена другому сотруднику, прежний исполнитель теряет доступ согласно правилам; история административного переназначения сохраняется.

## 4. Проверки Firestore Security Rules и серверных функций

Правила должны проверять не только роль, но и принадлежность ресурса:

1. Неавторизованный пользователь не читает и не изменяет закрытые коллекции.
2. Клиент читает только `clients/{request.auth.uid}`, свой договор и заявки с `clientUid == request.auth.uid`.
3. Клиент не может менять `clientUid`, `contractId`, номер, статус, исполнителя, отдел, системную историю или роль.
4. Клиент может добавлять только комментарий с автором, равным его UID, в собственную заявку и только при допустимом статусе.
5. Сотрудник не может назначить себя администратором, поменять владельца заявки или прочитать заявки вне своей разрешённой области.
6. Серверные события/аудит нельзя создавать или переписывать напрямую из браузера.
7. Администраторские изменения проверяются по доверенной роли, а не по полю из тела документа.
8. Любое разрешение на список документов должно быть совместимо с запросом Firestore; фильтрация после получения всей коллекции не является защитой.

Cloud Functions/Admin SDK обходят Firestore Security Rules, поэтому каждая функция обязана сама проверять вызывающего пользователя, роль, входные поля и права на целевой объект.

## 5. Миграция: соответствие старых и новых сущностей

| Старые данные | Новые данные | Особое внимание |
|---|---|---|
| `users[].id` | `users/{uid}` | соответствие старого сотрудника Auth UID; не генерировать автоматическую связь по одному имени |
| `clients[].id` | `clients/{uid}` | клиентские записи без Auth UID требуют подтверждённого процесса привязки |
| `contracts[].clientId` | `contracts.clientUid` | сверить связь в обе стороны с `clients.contractId` |
| `tickets[].clientId` | `tickets.clientUid` | включая служебные записи `isStaff` |
| `tickets[].assigneeId` | `tickets.assigneeUid` | сверить ссылку на существующего сотрудника |
| `tickets[].comments[]` | `tickets/{id}/comments/{id}` | сохранить автора, тип, текст и исходную дату |
| `tickets[].history[]` | `tickets/{id}/events/{id}` | сохранить старого автора/время; отметить неизвестные или публичные идентификаторы |
| `tickets[].recurrence` | поля повторения заявки | проверить шаблоны и связь `recurringParentId` |

Миграционный скрипт должен:
- поддерживать dry-run без записи;
- выдавать отчёт по количеству записей, потерянным связям и неоднозначным соответствиям;
- не переносить открытые пароли и PIN в новые документы;
- не создавать Auth-пользователей автоматически без утверждённой процедуры проверки личности;
- быть идемпотентным и сохранять mapping старых ID к новым;
- иметь backup и проверяемый откат.

## 6. Что нужно выяснить перед написанием рабочих Rules

- Текущие Firestore Rules и включённые Auth providers в Firebase Console.
- Полный перечень операций приложения для каждой роли, включая редактирование, удаление, назначение и повторяющиеся заявки.
- Способ выдачи первичных учётных данных после ручного одобрения (лично/через администратора/другой защищённый канал).
- Схема аутентификации без SMS/email и требования к восстановлению доступа.
- Политика хранения отклонённых заявок и повторной подачи.
- Правила привязки нескольких договоров к одному клиенту и нескольких клиентов к одной компании.
- Нужен ли клиенту показ имени исполнителя, статуса и части истории заявки.
- Нужно ли хранить служебные заявки сотрудников в той же коллекции и как отделять их от клиентских.

## 7. Безопасное ограничение текущего этапа

Этот документ не содержит готовых для деплоя Firestore Rules. Нельзя открывать доступ на основании предположений о ролях или данных. Следующий технический шаг — завершить аудит операций по ролям и проверить текущие Firebase Rules/Auth providers; затем подготовить Rules и тесты для Firebase Emulator Suite.
