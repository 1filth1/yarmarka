# Yarmarka CRM — план безопасной миграции

> Статус: проектирование. Этот документ описывает целевую архитектуру и безопасную последовательность работ. Он **не** меняет Firebase, Firestore Rules или данные production.

## 1. Текущее состояние (аудит `index.html`)

Основной интерфейс сейчас реализован одним HTML-файлом. Клиентский SDK Firebase Firestore 10.8.0 используется напрямую из браузера.

Обнаруженные особенности и риски:

- Все основные сущности (`users`, `departments`, `clients`, `companies`, `contracts`, `tickets`, `categories`, `settings`) загружаются и сохраняются одним документом `crm_data/main`.
- Сохранение выполняется через `setDoc` всего состояния; параллельные изменения могут перезаписывать друг друга. Один документ также ограничен лимитом Firestore в 1 MiB.
- Данные копируются в `localStorage`, включая пользовательские и клиентские данные, а клиентская сессия хранится как `hd_client_session`.
- Вход клиента ищет номер договора, проверяет дату окончания и сравнивает пароль с `client.password` непосредственно в браузере. Для этого клиенту предварительно загружается общий массив договоров и клиентов.
- При регистрации клиент и первая заявка создаются в клиентском коде и попадают в общий объект состояния.
- Идентификаторы клиента и договора (`CURRENT_CLIENT_ID`, `CURRENT_CONTRACT_ID`) — переменные браузера, а не доказательство личности.
- Сессия сотрудника также восстанавливается из `localStorage`; PIN проверяется клиентским кодом.
- Роли и ограничения интерфейса (`isAdmin()`, `applyPermissions()`) применяются только в браузере и не защищают данные в Firestore.
- В коде есть скрытый вход по сочетанию Ctrl+Shift+S и статическому коду. Его необходимо убрать в рамках перехода на нормальную авторизацию.
- В `seedData()` присутствуют демонстрационные учётные записи и PIN-коды. Их нельзя переносить в production как реальные учётные данные.

Следствие: скрытие разделов интерфейса не изолирует данные. До внедрения серверных правил и авторизации нельзя считать текущую схему безопасной для персональных данных, договоров и переписки.

## 2. Целевая архитектура

### Идентификация

- Использовать Firebase Authentication для сотрудников и клиентов.
- Каждому человеку соответствует Firebase Auth UID.
- Не считать PIN, пароль в документе, URL, локальную переменную или значение из `localStorage` подтверждением доступа.
- Роли `admin`, `staff`, `client` назначаются доверенным серверным кодом (например, custom claims) либо защищённым профилем, который пользователь не может менять сам.
- Клиентский аккаунт связывается с конкретным UID; связь с договором создаётся только после серверной проверки права на регистрацию.

### Данные

Перейти от общего документа к отдельным коллекциям. Предварительная схема (окончательные поля уточняются после полного аудита всех операций приложения):

- `users/{uid}` — профиль сотрудника и доверенная роль.
- `clients/{uid}` — профиль клиента, связанный с Auth UID.
- `companies/{companyId}` — компании.
- `contracts/{contractId}` — договоры и привязка к клиентскому UID.
- `tickets/{ticketId}` — заявки с полями владельца (`clientUid`), назначенного сотрудника и отдела.
- `tickets/{ticketId}/messages/{messageId}` — сообщения, если аудит подтвердит, что это удобнее текущей вложенной структуры.
- `departments/{departmentId}`, `categories/{categoryId}`, `settings/{settingId}` — справочники и настройки с отдельными правами доступа.

Клиент получает только свои профиль, договор(ы), заявки и сообщения. Сотрудник получает только разрешённые ему данные согласно роли и отделу. Администраторские операции выполняются по отдельным правилам.

### Серверная проверка

- Firestore Security Rules проверяют UID, роль, принадлежность заявки и договора, а также допустимые поля записи.
- Критичные действия (регистрация по номеру договора, привязка UID к договору, назначение ролей, административные изменения) выполняются доверенной Cloud Function или другим серверным компонентом.
- Проверка срока договора и права на регистрацию не должна полагаться на JavaScript браузера.
- Никаких правил вида «разрешить чтение/запись всем авторизованным» для коллекций с персональными данными.

## 3. Разделение интерфейсов

Можно оставить одну кодовую базу и разнести интерфейсы по разным точкам входа, например `/staff/` и `/portal/`, либо по поддоменам. Это организационное разделение, а не граница безопасности: доступ в любом случае обеспечивает Auth + Firestore Rules + серверная проверка.

До выбора URL можно проектировать независимые модули авторизации и доступа к данным.

- [ ] Написать Firestore Security Rules по утверждённой схеме.

### Этап 4 — миграция данных

- [ ] Выполнять миграцию production только после отдельного согласования, проверенной резервной копии и плана отката.

### Этап 5 — переключение и удаление старой схемы

- [ ] Переключить клиентский портал на новые API и коллекции.
- [ ] Проверить сценарии клиента и сотрудника в тестовой среде.
- [ ] Переключать production по согласованному плану с возможностью отката.
- [ ] Удалять старые поля с открытыми паролями и старый общий документ только после подтверждения успешной миграции и отдельного разрешения.

## 5. Критерии готовности

- Неавторизованный пользователь не может читать или изменять закрытые данные.
- Клиент не может получить чужой договор, заявку или переписку даже при ручном изменении запросов в браузере.
- Изменение роли или UID через DevTools не даёт дополнительных прав.
- Критичные проверки выполняются на доверенной стороне.
- Правила доступа покрыты автоматическими тестами.
- Миграция воспроизводима, сверяема и имеет проверенный сценарий отката.
- Существующий рабочий процесс CRM проверен на тестовых данных.

## 6. Ограничения текущего этапа

На этом этапе не выполняются операции в Firebase Console, не меняются Firestore Rules, не создаются и не удаляются Auth-пользователи, не читаются и не перезаписываются production-документы. Сначала завершаем аудит и готовим тестовую схему.
