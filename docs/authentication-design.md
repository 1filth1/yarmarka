# Yarmarka CRM — схема авторизации по логину и паролю

> Статус: проектирование для тестовой среды. Документ не меняет Firebase Console, Authentication, Firestore Rules или production-данные.

## 1. Принятое решение

Использовать уникальный логин и стойкий пароль без SMS и email. Проверка пароля выполняется только доверенным backend. После успешной проверки backend выдаёт Firebase Custom Token, а клиент обменивает его на Firebase Auth session.

Регистрация сотрудника отделена от создания учётной записи: публичная форма создаёт только заявку `pending`. Firebase Auth user и роль `staff` появляются только после ручного одобрения администратора и завершения активации.

## 2. Компоненты

- **Firebase Authentication** — сессии, ID tokens и refresh tokens. Клиент входит через `signInWithCustomToken`.
- **Cloud Functions (2nd gen)** — публичная подача заявки, вход по логину/паролю, активация, одобрение/отклонение, смена/сброс пароля и административные действия.
- **Firestore** — заявки на регистрацию, профили, роли, привязка логинов и служебные записи rate-limit/audit.
- **Firebase App Check** — дополнительная защита публичных callable endpoints от простого автоматизированного злоупотребления. App Check не заменяет авторизацию и rate-limit.

## 3. Модель идентификаторов и данных

Предварительные коллекции:

- `staffApplications/{applicationId}`: `fullName`, `phone`, `requestedDepartmentId`, `status` (`pending|approved|rejected`), `createdAt`, `reviewedAt`, `reviewedByUid`, `rejectionReason` (если нужен), `activationExpiresAt`.
- `staffProfiles/{uid}`: `fullName`, `phone`, `departmentId`, `status` (`active|disabled`), `createdAt`, `approvedAt`, `approvedByUid`.
- `loginIndex/{normalizedLogin}`: `uid`, `passwordHash`, `passwordHashVersion`, `status`. Документ доступен только Admin SDK; клиентским SDK чтение/запись запрещены.
- `securityEvents/{eventId}`: аудит входов, сбросов, одобрений и блокировок без записи паролей, активационных кодов или токенов.
- `loginAttempts/{key}`: серверные счётчики/окна попыток или эквивалентное хранилище rate-limit. Должны быть недоступны клиентам.

Логин уникален после нормализации (trim + lowercase для допустимого набора символов). Не использовать телефон как пароль или как доказательство личности. Номер телефона из формы — контактная информация для ручной проверки.

## 4. Жизненный цикл регистрации и активации

1. Публичная форма отправляет ФИО, телефон, желаемый отдел и выбранный логин. Пароль на этом шаге не создаётся.
2. Callable function `submitStaffApplication` валидирует поля, применяет App Check и rate-limit, проверяет дубликаты активных/ожидающих заявок и сохраняет заявку `pending`. Ответ не раскрывает сведения о других заявителях.
3. В административном разделе администратор проверяет данные вручную и выбирает утверждённый отдел.
4. Callable function `approveStaffApplication` проверяет custom claim `admin == true`, статус заявки и доступность логина. Она атомарно переводит заявку в `approved`, создаёт ограниченную активацию с одноразовым случайным кодом и сроком действия, фиксирует администратора и отдел.
5. Администратор передаёт одноразовый код лично/по согласованному вне системы защищённому каналу. SMS и email не используются.
6. Сотрудник открывает экран «Активировать аккаунт», вводит логин, одноразовый код и устанавливает свой стойкий пароль. Callable function `activateStaffAccount` проверяет хеш кода, срок, число попыток и статус заявки; затем создаёт Firebase Auth user, сохраняет Argon2id password hash в серверном login index, назначает custom claims `staff`, UID и отдел, помечает заявку завершённой. Операция должна быть идемпотентной и защищённой от повторного использования кода.
7. Сотрудник входит обычным логином и паролем.

До завершения шага 6 нет Firebase Auth account с ролью сотрудника и нет доступа к рабочим данным. Заявка `pending` или `approved` сама по себе не является сессией.

## 5. Вход по логину и паролю

1. Клиент вызывает callable function `loginWithPassword` с логином и паролем по HTTPS.
2. Функция нормализует логин, проверяет серверный rate-limit и находит запись login index через Admin SDK.
3. Функция проверяет пароль по Argon2id hash. Пароль, хеш и диагностические детали никогда не возвращаются клиенту и не логируются.
4. Для отсутствующего логина и неверного пароля возвращается одинаковая общая ошибка, чтобы не раскрывать существование аккаунтов.
5. Функция проверяет статус профиля и актуальность роли. При disabled/revoked аккаунте вход запрещён.
6. При успехе функция создаёт Firebase Custom Token для соответствующего UID и возвращает его клиенту. Клиент вызывает `signInWithCustomToken(auth, token)`.
7. Firebase ID token содержит доверенные custom claims; Firestore Rules проверяют их вместе с UID и владельцем ресурса.

Пароль не передаётся в Firestore и не хранится в браузерном `localStorage`. Клиент не получает доступ к коллекции `loginIndex`.

## 6. Требования к паролям и защите входа

- Минимум 14 символов; разрешить длинные парольные фразы и менеджеры паролей.
- Не требовать искусственных комбинаций регистра/цифр/символов, не заставлять регулярно менять пароль без признаков компрометации.
- Отклонять известные слабые/часто используемые пароли; не обрезать пароль и корректно обрабатывать Unicode.
- Хранить только Argon2id hash с уникальной солью и актуальными параметрами. Параметры подобрать нагрузочным тестом под Cloud Functions; предусмотреть версионирование и rehash при успешном входе.
- Rate-limit по нормализованному логину и IP/источнику с прогрессивной задержкой и аудитом; не создавать простой механизм блокировки чужого аккаунта одним набором неверных паролей.
- Использовать одинаковое сообщение ошибки для неизвестного логина и неверного пароля.
- Не писать секреты в логи, Analytics, crash reports или URL. Не сохранять пароль/активационный код в localStorage.
- Настроить App Check, CORS/доступ callable только нужным приложениям, мониторинг аномалий и оповещения.
- HTTPS обязателен. Firebase Custom Token короткоживущий; Firebase Auth управляет последующей сессией. При блокировке пользователя сервер отзывает refresh tokens и отключает аккаунт.
- Проверять права на backend и Firestore Rules, а не только в UI.

## 7. Восстановление доступа без SMS/email

Сотрудник обращается к администратору и проходит ручную проверку личности. Администратор инициирует серверную процедуру сброса. Backend создаёт новый одноразовый активационный код с коротким сроком действия; сотрудник получает его лично/через согласованный защищённый канал и задаёт новый пароль. Старый пароль немедленно перестаёт работать. Событие аудируется. Администратор не видит и не задаёт постоянный пароль сотрудника.

## 8. Роли и сессии

- Роли в custom claims назначаются только Admin SDK из доверенных функций.
- Публичная регистрация никогда не принимает роль, UID, статус или права из тела запроса.
- `pending` / `rejected` заявки не имеют доступа к закрытым данным.
- Сотрудник читает/изменяет только назначенные ему заявки (`assigneeUid == request.auth.uid`) и разрешённые ему поля.
- Администратор читает все заявки и управляет сотрудниками/заявками регистрации.
- Клиентская роль и доступ к клиентским данным изолированы отдельными правилами.
- Изменение роли/отдела, отключение аккаунта и сброс пароля требуют серверного действия и записи аудита.

## 9. Обязательные тесты

- Публичный запрос не может создать активный профиль или назначить роль.
- Пользователь не может самостоятельно одобрить заявку или изменить статус/отдел после подачи.
- Одноразовый код истекает, имеет лимит попыток и не может быть использован повторно.
- Неподтверждённый/отклонённый/отключённый пользователь не получает Custom Token.
- Неверный пароль и неизвестный логин дают одинаковую внешнюю ошибку.
- Rate-limit срабатывает и не позволяет массовый перебор.
- Ни один клиентский запрос не читает login index/password hash.
- Custom claims нельзя изменить из браузера.
- После отзыва сессии старые refresh tokens перестают работать.
- Проверить права на заявки для сотрудника, администратора и клиента через Firebase Emulator Suite.

## 10. Важное ограничение

Этот проект использует кастомный парольный слой поверх Firebase Custom Auth. Это требует аккуратной реализации и поддержки backend. Перед production необходимо провести security review, проверить rate-limit в распределённой среде, управление секретами, обработку ошибок и процедуру восстановления. Не реализовывать собственную криптографию: использовать проверенную Argon2id библиотеку и Firebase Admin SDK.

На текущем этапе ничего не развёртывается и не меняется в Firebase Console или production.
